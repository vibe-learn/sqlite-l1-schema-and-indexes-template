        # sqlite — Схема и индексы

        Homework-шаблон для урока **l1_schema_and_indexes** (Схема и индексы) на платформе Vibe Learn.

        ## Что делать

        На Go с modernc.org/sqlite (чистый Go, без CGO) реализуй слой схемы магазина. Функции:
OpenDB(dsn) — открывает БД и СРАЗУ включает PRAGMA foreign_keys=ON; Migrate(db) —
идемпотентно создаёт users и orders с корректными REFERENCES, UNIQUE(email),
CHECK(total_cents>=0) и индексами (user_id, created_at) и частичным по status='paid';
InsertOrder(db, ...) — должен вернуть ошибку при ссылке на несуществующего юзера;
UsesIndex(db, query) — парсит EXPLAIN QUERY PLAN и сообщает, использован ли индекс
(SEARCH ... USING INDEX). Тесты гоняют на :memory:-базе: проверяют, что без foreign_keys=ON
«сирота» вставляется, а с ON — отвергается; что запрос по (user_id, created_at) даёт SEARCH,
а не SCAN; и идемпотентность миграции.

## Контекст (из transfer-задачи урока)

Тебе отдали SQLite-базу интернет-магазина. Схема (упрощённо):
orders(id INTEGER PRIMARY KEY, user_id INTEGER REFERENCES users(id), status TEXT,
total_cents INTEGER, created_at INTEGER), users(id INTEGER PRIMARY KEY, email TEXT).
Проблемы в проде:
(1) аналитики нашли заказы с user_id, которых нет в users (битые ссылки), хотя в схеме
    стоит REFERENCES;
(2) запрос «суммы заказов конкретного юзера за период» (`WHERE user_id=? AND created_at
    BETWEEN ? AND ?`) делает полный скан;
(3) дашборд «список оплаченных заказов» (`WHERE status='paid'`) тоже медленный, а оплаченных
    — лишь ~5% строк.

**Вопрос:** распиши:
(a) почему появились битые ссылки несмотря на REFERENCES и как это починить ВПЕРЁД (и можно
    ли заставить SQLite найти уже существующие нарушения);
(b) какой индекс под запрос (2) и почему именно такой порядок колонок;
(c) стоит ли тут частичный индекс под (3), и какой trade-off;
(d) честно: после включения PRAGMA foreign_keys=ON исчезнут ли УЖЕ существующие битые
    ссылки сами, или их надо вычищать отдельно?

## Recap из урока

- У каждой обычной таблицы есть скрытый **rowid** (64-бит) — ключ кластеризации. `INTEGER PRIMARY KEY` (именно так) — его псевдоним, самый эффективный PK.
- **FOREIGN KEY по умолчанию ВЫКЛЮЧЕНЫ** — главный фут-ган. Нужен `PRAGMA foreign_keys=ON` на каждом соединении, вне транзакции; иначе тихие сироты. `PRAGMA foreign_key_check` ищет существующие нарушения.
- `WITHOUT ROWID` кластеризует таблицу по PRIMARY KEY (обязателен) — выгодно для словарей с текстовым/составным ключом.
- Индексы: обычные, составные (leftmost prefix), **покрывающие** (ответ из индекса), **частичные** (`... WHERE`), **по выражению** (`lower(x)`). Подбирай под форму запроса.
- `AUTOINCREMENT` почти всегда **не нужен**: `INTEGER PRIMARY KEY` и так автоинкрементен. AUTOINCREMENT лишь запрещает переиспользование id ценой оверхеда.

        1. Платформа Vibe Learn создаёт копию этого репо в твоём GitHub-аккаунте по клику «Начать домашку» на странице урока (через GitHub `/generate`, codecrafters-pattern).

        ## Локальное окружение

        - Go 1.22+
        - SQLite встроена — **никакого сервера и docker-compose**. БД это один файл (`DATABASE_PATH`) или `:memory:` в тестах. Драйвер `modernc.org/sqlite` — чистый Go, без CGO, так что CI собирается без компилятора C.

        ## Запуск

        ```bash
        # Прогнать тесты (бегут на :memory:-базе, ничего поднимать не нужно)
        go test ./...

        # Запустить main (создаёт схему, печатает marker; замени stub на реализацию)
        go run .

        # На файловой БД (нужно для WAL/concurrency-уроков):
        DATABASE_PATH=./app.db go run .
        ```
